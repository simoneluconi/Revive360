# 15 — Porting to the Gear 360 (2017), SM-R210: offline survey (ARB2)

What carries over from the C200 work to the SM-R210, and what has to be redone. Everything here
comes from the stock image `R210GLU0ARB2_180201_1739_REV00_user.bin` (SHA-256 `81765495…8324`,
the last R210 firmware), with no camera involved. Surveyed on 2026-10-29.
Nothing here has been tried on an R210 yet. Items marked **(hw)** need the camera.

## Summary

| Area | R210 vs C200 | Effort |
|---|---|---|
| SLP container, CRC, `/etc/parttab` | identical (10 parts, same partition map) | none: `slp_pack.py`, `fw_build.sh` reuse |
| Boot snapshot on p8 | identical (bootloader restore, kernel `noresume`, no `/etc/snapshot`) | none: `p8_invalidate.sh` still needed after each flash |
| SD update trigger | same idea, different file name | small: `install.sh`, `make_firmware.sh` |
| SD hook `info.tg` → dfmsd | same gate (different binary) | none expected **(hw)** |
| Wi-Fi softAP | BCM43455, same `wlan.sh softap` + `hostapd` + `dnsmasq` | none expected **(hw)** |
| RAW (`ssifdump`) | same RTOS debug command and dump names; the recipes free the buffer first; 10-bit | done: a runtime RTOS patch ([RAW](#5-raw)) |
| Shim/plugin into `di-camera-app` | **app rewritten** (`CAPP*`, `AppNet::*`) | rewrite the R210 side of the plugin |
| Stock OSC server ("Connect to Street View") | **R210 only** | optional stock-firmware path, no flash |

## 1. Firmware image

`slp_unpack.py` output: model `SMR210`, name `SMR210GLU0ARB2`, build `VER_Rev0.7`, 10 parts, no
trailer. The rootfs is part 6 (132 MB lzop, ext4 `rootfs`), opt is part 7 and the snapshot is part 9.
The stored CRCs follow the same `zlib.crc32 ^ 0xFFFFFFFF` rule as the C200 (`slp_unpack.py` reports
them as "BAD" because it compares against the plain zlib value). `/etc/parttab` is byte-for-byte the
C200 table (`rootfs.img` → p9, `snapshot.img` → p8, `rImage` → p12).

`/etc/info.ini`: `Model=SMR210; Build=R210GLU0ARB2; Date=2018.02.01`.

Bootloader (part01) strings: `> snapshot boot`, `snapshot img_load start!`, `Invalid snapshot
image.`, cmdline `root=/dev/mmcblk0p9 rw rootfstype=ext4 rootwait noresume`. So, as on the C200,
a normal boot restores the factory snapshot from p8, and a flashed rootfs only runs after p8 is
invalidated.

## 2. SD update trigger (di-camera-app, `CAPPFwUpgradeMode` / `CAPPPowerOnMode`)

- **File name.** `getFwFileInCard()` scans `/mnt/mmc/` for a user image: a name exactly 39
  characters long that starts with `R210GL` and ends with `user.bin` (the stock name, for example
  `R210GLU0ARB2_180201_1739_REV00_user.bin`), or 43 characters `FTMA_R210GL…eng.bin` for an
  engineering image. When there is none it falls back to the old names `smr210.bin` /
  `smr210_eng.bin` (`setOldFwName`, `isDeviceFwNewName`). A stock-named file wins over
  `smr210.bin`, so the card must hold only one image.
- **Unattended start.** `CAPPPowerOnMode` runs the update at power-on when the boot key is
  `E_BOOT_KEY_FW` **and** `/mnt/mmc/fwupgrade.txt` exists.
  `CAPPSystemManager::getDevmanBootFwUpdateKeyStatus()` returns 4 when
  `device_get_property(0xd, 1)` (`PROP_KEY_STATE_SHUTTER`) reads pressed. 4 maps to
  `E_BOOT_KEY_FW`. 5 (`memory/sysman/fwup_key_check` = 1, from `/sys/class/sec/key/fwup_keys`) maps
  to `E_BOOT_KEY_ODIN_FW`. So the procedure is the same as on the C200: **hold the shutter
  button while powering on**, with the image + `fwupgrade.txt` on the card **(hw)**.
- **Battery.** `CAPPBattManager::isFwUpgradeBatteryPercentage()`: percentage **> 19**.
- **Validation.** `isSuccessCrc()` → `fw_validate(name, project_name, 1, 0)` in
  `libfirmware-upgrade.so`, which checks the SLP header and CRCs, as on the C200. No version
  comparison was found, so reflashing the same version (our repack keeps the ARB2 header) is fine.

## 3. SD hook (`info.tg`)

`libfactory-mode.so` differs from the C200's (md5 `a98a759a…`, dfmsd `2a2e8604…`), but
`dfms_check_factory_mode` has the same logic: when `/sdcard/info.tg` exists, its first line (trimmed)
names a file under `/sdcard/`, and when that file exists the mode is 2 (script). `info.tgw` → 3,
`info.tgx` → 4. There is no fuse or key gate. `di-camera-app` logs `[APP] ( info.tg )` at card init.
`/usr/bin/st` and `libshell-command.so` (`st cap back …`) are present. So the one-shot
`p8_invalidate` hook and an SD probe should work unchanged **(hw)**.

## 4. Wi-Fi

`wlan.sh` (same structure as the C200) loads `wlan_apsta_bcm43455.bin` for `softap`. `hostapd`,
`wpa_supplicant` and `/usr/bin/dnsmasq` are in the rootfs, but `mobileap-agent` is not. Storage:
`/sdcard` → `/mnt/mmc` → `/opt/storage/sdcard`, the same as the C200.

## 5. RAW

The R210 RTOS (part05, 12.3 MB) has the same back-end debug command (`st cap back [command]`,
`CBackend_uniTest`, `Back SSIFDump Flag On!!/Off!!`) and the same dump names
(`ssif_front_%dx%dx%d_%d_10bit(16bit).raw`, `ssif_rear_…`). Sensor class `CIQ_SensorIF_S5K2M8SX`.
All RTOS addresses from [14](14_raw_capture.md) (flag byte, the FILE_OPEN cache bug that `rawfix`
works around) are AQK1-specific and must be found again in the R210 part05.

**Status: working since 2026-10-31**, both lenses, through the same `raw` setting as the C200
([The fix](#the-fix-2026-10-31)). The dumps are **10-bit**, not 12-bit as on the C200
([Format](#format-10-bit-against-the-c200s-12)).

### On the hardware, 2026-10-29: the camera restarted

`st cap back unitest ssifdump on` works on ARB2 ("Back SSIFDump Flag On!!", flag at object
+0x19, set in the same `uniTest` code). But a photo with the flag on, in a lit room, **restarts the
camera** about two minutes later. The card is left with an empty `ssif_rear_5824x2912x2896_0_10bit(16bit).raw`
and no front file. The RTOS log stops after `STILL_PREPROC`.

The R210 plugin has its own `rawfix`. Like the C200's, it points libcapture's `fopen` slot at a
wrapper; it also hooks `fwrite`, `fclose` and `mmap`. It writes every open, the first write to each
card file, a write from a buffer that cannot be read (skipped instead of crashing the app) and any
failed `/dev/mem` mapping. The log goes to `g360r/log/rawfix.log` on the card, synced line by line
so it outlives the restart. Three shots gave the same log:

- `active_align_check.chk` and `active_align_check_rear.chk` opened for reading (missing, as on the C200);
- `ssif_rear_…raw` opened for writing, with a clean name (once the dump worked, the rear name came
  as `….raww` as on the C200: the same cache bug, cut by `rawfix`);
- no front open at all, not even a garbled name (every libcapture `fopen` is logged), and **no
  `FILE_WRITE`** and no failed mapping.

So nothing goes wrong on Linux: the A7 stops between the rear open and its first row.

The dump itself (`FUN_80282e84`, the C200's `0x80284b88`) is the same code. It writes the front half
of the SSIF image (material 0x15000), then the rear half at address + stride/2, through
`FUN_801e5664`, which **returns before opening when the address is 0**. The difference is in the
recipes. On the C200, `RecipeNormal` releases the SSIF buffer early (a link after the sensor's
`pSensorBPPout` material) **only when `ssifdump` is off**: `if (FUN_8058ee44(flags) != 1) { …
FUN_8058fa34; FUN_80327784; }`. On ARB2 the same link (`FUN_80575420` + `FUN_80325b84`, the same
functions moved) is made **unconditionally** in every recipe. The flag's getter
(`FUN_80574780`) has a single caller, the dump. So when the dump runs, the SSIF buffer is already
gone and its address is 0:

1. the front is skipped (address 0), so no open reaches Linux;
2. the rear opens (address 0 + stride/2 is not 0);
3. its first row is read from that address and the A7 dies, then the watchdog restarts the camera.

Everything seen fits.

### The fix, 2026-10-31

The normal 360 still is built by `FUN_802a9c40` ("Create Normal Recipe"): dual lens →
`FUN_802abf50`, or its twin `FUN_802ab6b4` (the same chain with the time-lapse resizers), both
"Screen GPU Stitch" recipes, the C200's `FUN_802ae1e0`. In each, the link is four calls after the
`pSensorBPPout` material:

```
802ac18c  ldr  r0, [fp, #-0x20]     ; the SSIF material   (FUN_802ab6b4: 802ab8e8, [fp, #-0x1c])
802ac194  bl   FUN_802522d4         ; its image
802ac1a4  bl   FUN_8059dee4         ; new 8-byte link
802ac1b8  bl   FUN_80575420         ; init it with the image
802ac1c4  bl   FUN_80325b84         ; attach it to pSensorBPPout = free the SSIF buffer after it
802ac1c8  ...                       ; MakerNote material
```

The patch turns the first `ldr` into a branch past the last `bl` (`e51b0020` → `ea00000d`,
`b 0x802ac1c8`; `e51b001c` → `ea00000d`, `b 0x802ab924`). The skipped code only uses r0, r1, r3,
r4, r5 and r6, and the code after it loads each of them again before reading it (`-O0` code, every
value goes through the stack). What is left is the C200 with the flag on: the buffer is freed with
the recipe.

`g360rd` (`camera/src/raw.c`, words in `adapter_r210.c`) writes the two words through `/dev/mem`
(the RTOS's RAM is mapped 1:1) **at start-up, whether `raw` is on or not**:

- the RTOS is loaded again from eMMC at every boot, so nothing stays;
- before writing, all six words must hold their ARB2 values (the two to patch and the `bl` words at
  `802ac1b8`, `802ac1c4`, `802ab914`, `802ab920`), or nothing is written and there is no `raw`
  setting;
- at start-up, because the A7 has caches the A9's write does not reach: once a still has run, the
  old instructions may stay cached there, and a patch written later could miss the next shot. Before
  the first still, nothing of the recipe has been fetched yet.

With the patch on and the flag off, a still is as before: 2.1 s, no dump (tested). The flag is the
same `uniTest` object's +0x19: the singleton `FUN_801ec334` returns `0x81884898`, so the byte is at
**`0x818848b1`** (read 1 and 0 with `ssifdump on` and `off`). From there on it works like the C200:
the flag watched and re-armed, `rawfix`, and the dumps moved to `DCIM/RAW/` after their photo.
The low-light patch of both cameras ([14, Low light](14_raw_capture.md#low-light)) is in the same
word table.

Hardware, 2026-10-31: shots 249 (by hand) and 251 (from the app, after a cold boot), both lenses,
JPEG in 8 s instead of 2 s (the dump writes one row per message). DNG from the app and from
`tools/raw/ssif2dng.py`, pixel-identical, colours as the JPEG with the C200's colour matrix.

### Format: 10-bit against the C200's 12

| | C200 (AQK1) | R210 (ARB2) |
|---|---|---|
| Dump name | `…_7776x3888x3950_…` | `…_5824x2912x2896_…` |
| Per lens | 3888 × 3950 rows | 2912 × 2896 rows |
| Bits | **12** (values << 4) | **10** (values << 6: the low 6 bits are always 0, max 65472 = 1023 << 6) |
| Optical black | rows 0–15 (~128 on 12 bits), image from row 40 | none: every row is image; black 64 (10 bits) from the dark corners |
| Image | 3888 × 3888 from row 40 | 2896 × 2896, the JPEG's lens size, centred (from column 9) |
| CFA | RGGB | GRBG (from an odd column it is RGGB) |
| White | 4095 | 1023 |
| Size per photo | 2 × 30.7 MB | 2 × 16.9 MB |

The file names say "10bit(16bit)" on both cameras, so the bit depth was read from the data. GRBG
against GBRG was settled against the JPEG: the raw R/G and B/G follow the JPEG's with a correlation
of +0.79 / +0.81 in GRBG and −0.29 / −0.27 the other way.

**Why 10 and not 12 (offline, 2026-10-31).** Each RTOS has a table of sensor modes for the SSIF,
and its first byte is the bit width (read by R210 `FUN_8020d0f8`, C200 `FUN_802211e4`, then
`convertToBFBitSize`/`convertToASFFBitSize`). On the C200 (`FUN_80220aec`) the still mode 21
`eSensorModeVideoFull` is `7776, 3950, …, 40 …`, the dump's shape with its 40 black rows, with code
**2**, while the 10-bit low-power modes have **1**. On the R210 (`FUN_8020c8d4`) **every** mode is
code 1, including mode 22 (5824 × 2896, the dump). The dump (`FUN_80282e84`) writes the SSIF
material as it is, with no shift. The sensor is different too: a Samsung S5K2M8SX (still mode
`FUN_8023c034`, "Video Full for still capture(2912x2896)"; no mode writes the CSI data format
register 0x0112) behind a Lattice XO3L FPGA with a fixed MIPI-to-sLVDS bitstream; the C200 has a
Sony IMX147. 12 bits would need the sensor switched to RAW12 (support unknown), an FPGA bitstream
that carries it (not available) and the table byte changed (`0x8189ae18`, 1 → 2): the last alone
would give garbage. So the R210's RAW stays 10-bit.

The converters read both on a 12-bit scale (>> 4: the R210's values then step by 4, white 4092) and
tell the camera by the shape: more rows than pixels per row is a C200. 10 bits give a quarter of the
levels: less room to pull shadows and highlights than on the C200, still the sensor's data before
demosaicing, white balance, sharpening and JPEG.

## 6. di-camera-app: what the shim and plugin can use

The R210 app (3.6 MB, stripped but with 6326 dynamic symbols) is a rewrite. It is organised as
`CAPP*Mode` state classes plus an `AppNet::` service layer of singletons (`getInstance()::inst`
function-local statics).

Present, same names as on the C200: `UI_Get_Value`, `UI_Set_Value`, `CUINETUtil::{Stop,Restart}PowerTimer`,
`IsTimelapseMode`, `IsTimelapseCapturing`, `RefreshStatusLCD`, `CUINETDlnaMan::StopDlna`,
`CUINETFuncDLNA::dlna_mpeg_stop`, `CUINETFuncRemoteShot::process_movie_rec{,_stop}`,
`DlnaGetDeviceDescUrl`, and the `mm_camera_*` imports the shim interposes.

Missing: `NETCameraMenuMan::*` (the C200 remote-menu table), `Ui_Get_Common_Run_State`,
`CUINETDlnaMan::Inst`/`StartDlna(bool,bool)` (now `StartDlna(INETDlnaReciever*, bool, bool)`),
`CUINETFuncDLNA::Inst`, `CUINETFuncRemoteShot::Inst`, `SetUserDataMCB`,
`UI_Send_Message_Changed_Attributes`.

R210 replacements (cleaner than the C200 route):

- **Settings: `AppNet::Menu::CManager`.** `getValue/setValue(Type, int|const char*)`,
  `getValueStr`, `getValueStrByIndex`, `getSize`, `getTitle`, `getIndex`. There are 44 types
  (`AppNet::Menu::toString`):
  `0 AutoPowerOff, 1 Beep, 2 Ev, 3 Format, 4 Hdr, 5 HdrMovie, 6 HdrForSDK, 7 HdrMovieForSDK, 8 IsoRange,
  9 LandscapeHdrPhotoSizeDual, 10 LandscapeHdrPhotoSizeSingle, 11 Led, 12 LoopingVideoRecordTime,
  13 LoopingVideoRecordTimeDisable, 14 LoopingVideoSizeDual, 15 LoopingVideoSizeSingle, 16 Mode,
  17 PhotoSizeDual, 18 PhotoSizeSingle, 19 RatioOffset, 20 Reset, 21 Sharpness, 22 StreamQuality,
  23 StreamResolutionForiOs, 24 StreamResolution, 25 SwitchLens, 26 TimelapsePeriod,
  27 TimelapseVideoSizeDual, 28 TimelapseVideoSizeSingle, 29 Timer, 30 VideoSizeDual,
  31 VideoSizeSingle, 32 Wb, 33 Windcut, 34 DefaultLens, 35 StreamQualityProfileDual,
  36 StreamQualityProfileSingle, 37–40 LiveBroadcastingSize{Dual,Single}{,iOS}, 41 NightPhoto,
  42 NightPhotoForSDK, 43 LiveBroadcasting4KStreamBitrate`.
- **Still capture: `AppNet::Capture::CManager::start(bool)`.** Also `isCapturing`, `getRemainCount`.
- **Recording: `AppNet::Record::CManager::start/stop/pause/resume`.** Also `isRecording`,
  `isPaused` and the remaining time per type (video / looping / time-lapse).
- **Status: `CUINETUtil::Is{PhotoMode,VideoMode,Recording,DualLens,StbyState,TimerCounting,…}`,
  `GetBatterySOC`, `Get{Free,Used,Total}Space`.**
- `CUINETDlnaMan::__dlna_set_*` (mode, resolutions, ev, iso, wb, hdr, timer, led, beep,
  interval, …) is the remote path Samsung's phone app used, in case calling `Menu::CManager`
  directly misses a side effect.

Capture and recording must run on the app's ecore main loop, as on the C200 (the shim already
marshals plugin requests there).

## 7. Stock OSC server (R210 only)

The stock R210 firmware can serve the Open Spherical Camera API v1 by itself:

- Camera menu **Connect → "Connect to Street View"** (`CSLCDDrawConnectMenuMan::is_enable_google_street_view`,
  enabled when a usable SD card is in and the language is not Chinese) → `AppNet::OSC::CManager::startOSC`
  → softAP + `OSCServerStart` in `libdi-network-dlna-api.so`.
- SSID: `<model name>(<last 4 hex digits of the Wi-Fi MAC>).OSC` (`get_softap_ssid_for_osc`).
  WPA2-PSK password: 8 random decimal digits made once by `make_softap_password` (`rand()` seeded
  from `CLOCK_MONOTONIC`), stored in pref (3, 0x268), and regenerated only by a Wi-Fi reset. It
  cannot be computed, but the connect screen draws it (`draw_pairing_pw`), so a user can type it once.
- HTTP on port **80** (`/osc/info` reports `httpPort` 80), endpoints `/osc/info`, `/osc/state`,
  `/osc/checkForUpdates`, `/osc/commands/execute`, `/osc/commands/status`. `/osc/info` returns
  fixed placeholders (`serialNumber` "A1B2C3D4E5", `firmwareVersion` "01.01").
- Commands: `camera.startSession`, `updateSession`, `closeSession`, `takePicture`, `listImages`,
  `getImage`, `getMetadata`, `delete`, `getOptions`, `setOptions`. Options include `captureMode`,
  `exposureProgram`, `iso`, `shutterSpeed`, `whiteBalance`, `hdr`, `gpsInfo`, `dateTimeZone`,
  `remainingPictures`, `remainingSpace`, `totalSpace`, `batteryLevel`.
- Photos only (OSC v1 has no video commands).

This could give the app basic R210 support (photos, gallery, download, delete, battery and space)
with **no firmware change**, at the cost of the user starting Street View mode on the camera and
typing the 8-digit code once **(hw)**.

## Hardware probe, 2026-10-29 (stock AQC6)

`tools/r210_probe/` (`info.tg` → `probe.tg` → `g360r/r210_probe.sh`, read-only) ran on the user's
R210 on stock firmware and logged to the card. The probe made no sound: `paplay` gave nothing
audible, and the script now logs the player's exit code and falls back to `aplay`.

- **The SD hook works** on stock R210: `di-camera-app` (pid 254) launched `dfmsd` (pid 290),
  which ran the script as root about 27 s after power-on.
- **Firmware on the unit: `R210GLU0AQC6` (2017-03-17)**, older than ARB2. The project supports only the
  latest build per model, so the unit was updated to stock ARB2 first. **The SD update worked from
  AQC6**: stock ARB2 under both names (`R210GLU0ARB2_…_user.bin` and `smr210.bin`) plus an empty
  `fwupgrade.txt`, USB unplugged, shutter held while pressing power. Which of the two names AQC6
  picked is not known. A second probe run then read `Build=R210GLU0ARB2` from `/etc/info.ini`. The SD
  hook works on ARB2 too (dfmsd pid 289, script about 28 s after power-on).
- Sound: in the second run `paplay confirm.wav` returned 0 for all three beeps, and still nothing
  was heard. A sound test (`tools/r210_probe/sound.tg` + `g360r/r210_sound.sh`) played dfmsd's
  `sound play low_battery` (mm-sound, like the camera app), then `paplay` and `aplay`, and all
  three were heard. PulseAudio itself was fine (sink `alsa_output.0.analog-stereo`, 100 %, not
  muted). After the mm-sound play, the rt5659 switches `Ext Spk L` / `Ext Spk R` were **on**: most
  likely the camera's player switches the speaker on and plain `paplay` does not. The "before"
  state was not captured, so this is still a guess. Scripts on the R210 therefore run
  `amixer sset 'Ext Spk L' on` (and `R`) before their first beep. That fix is untested.
- Snapshot boot as on the C200: kernel cmdline `noresume`, dmesg stops at 2.1 s, and the uptime was
  about 27 s when the hook ran.
- Partitions match `/etc/parttab`. The SD card is `mmcblk1p1` with exFAT on `/opt/storage/sdcard`
  (`fmask=0022`). The rootfs is 91 % full (25 MB free).
- **LEDs: `led.0`–`led.6` (7)**, max 255, all `trigger=none`. The C200 has 5. The mapping is still
  to be found with `g360rd ledtest`.
- Keys: `Drime5 GPIO Keyboard` on `event0`. `/sys/class/sec/key/` has `power`, `power_key`, `rec`, `wifi`
  and `fwup_keys`.
- Battery: `/sys/class/power_supply/battery` (`capacity`, `status`, `voltage_now`, `temp`, `batt_temp`).
  Charger s2mu004.
- Wi-Fi: `wlan0`/`p2p0` down, the `dhd` driver is built in with an empty `firmware_path`. rfkill shows
  `bcm43455 Bluetooth` (soft-blocked), `phy0`, `brcmfmac-wifi`. Same layout as the C200.
- `systemctl` there has no `cat`.

## First modified image on the hardware, 2026-10-29

`./install.sh r210 flash` then `activate` on the user's R210 (ARB2). Results:

- **Flash and activation as on the C200.** The p8 hook changed page 0 from `SWSUSP` to
  `SWAPSPACE2` and listed our files in `/usr/share/g360r`. After a power cycle the camera cold-boots
  our rootfs, and `boot.sh` starts the controller about 29 s after power-on. The camera shows no
  factory screen during the activation. The hook beeped once the speaker switches were on.
- **Wi-Fi:** `netup.sh` works unchanged (`wlan.sh softap`, then `hostapd`: 5 GHz, channel 36/80 MHz,
  firmware `7.120.5 (C0 SoftAP feature)`). The app connects; status, storage and the file list work.
- **Bluetooth:** BlueZ there is 5.37 (Tizen): no `GattManager1.RegisterService`, only
  `RegisterApplication`. `g360r-ble` now falls back to it on an ObjectManager at `/org/g360r/gatt`.
  `ReadValue`/`WriteValue` keep Tizen's `(s address, y id, q offset)` arguments (same introspection
  as `libbluetooth-api.so`). Advertising works, but every `SetAdvertising` call answers "Failed"
  (logged once per run). Pairing over Bluetooth and Wi-Fi on demand both work.
- **Auto power off:** without a shim, the camera app's own `st app dev power` (handler
  `ui_shell_dev`: "[SET] AutoPower Timer Disable") sets its disable-auto-power-off flag, and a bare
  `st app dev` clears it. Both make the app save its preferences, so `adapter_r210` sends them only
  when a client comes or goes, plus every 10 min while held. Avoid `st app dev all|sound`: they also
  mute the camera.
- **Clock:** like the C200, the camera runs on a fixed +9 h zone (set to 19:33 UTC, its log read
  04:33). The adapter has `clock_local`, so the camera shows the phone's local time.
- **Wi-Fi under a fast upload:** twice, a full-speed upload to the camera (the 227 MB image, on
  the second try a 735 KB file) stopped after tens of MB. The radio firmware hung in AP mode:
  `hostapd` stayed alive, `wl ap` stopped answering 1, and no frame got through until the AP was
  brought up again (here only after the 10-minute idle timeout). The phone was then kept out by
  `max_num_sta=1`, because Android joins with a new random MAC. Fixes: `max_num_sta=3` +
  `ap_max_inactivity=30`; on the R210 three `wl ap` misses in a row count as a dead AP (re-brought
  up within a minute); big uploads are rate-limited (`curl --limit-rate`).
- **The app after a Bluetooth timeout:** the write that switches the Wi-Fi on got no confirmation
  once, and the app's wake then died silently on `TimeoutCancellationException`. Fixed in
  `BleSession`: a timeout is now an `IOException`, and the app retries, then joins anyway.
- **Updates without the card:** `g360rd` through `debug/upload` + `debug/restart?replace=`. The
  Bluetooth helper and scripts go through `debug/upload` + `debug/script`. Reboot is
  `POST /api/v1/power`, as on the C200.

## Second modified image: shim and plugin, 2026-10-29

Flashed with the card left in the camera (image uploaded at 1 MB/s, 217 s). `di-camera-app` maps the
shim (`shim-r210`, no interposers). The R210 plugin (`shim/g360r_plugin_r210.c`, on the card as
`g360r/libg360r_plugin.so`) reaches the app's managers through their exported unique singletons
(`_ZZN6AppNet4Menu8CManager11getInstanceEvE4inst`, checked against their `_ZGVZ…` guards):

- `menus` lists all 44 menus with title, value, value string and item count. `menu TYPE` gives the
  items (index = value "string"). `menuset` sets one and reads it back. `getValueStr*` return a
  `const std::string&`: one pointer to the characters (old libstdc++).
- `shot` is `CUINETFuncRemoteShot::process_capture`: a JPEG in about 2 s
  (`DCIM/100PHOTO/360_NNNN.JPG`, 5472×2736). `recstart`/`recstop` are the remote's movie record and
  stop (`360_NNNN.MP4`).
- `state` reads the `CUINETUtil::Is*` flags, including `IsTimelapseCapturing`.

`adapter_r210` (status `supported` since the hardware tests below) maps the protocol settings onto those menus: mode 16, lens 25,
photo size 17/18 and video size 30/31 (dual/single menus), timer 29, time-lapse interval 26, loop time 12,
EV 2 (0.1 steps, offered in 0.5), ISO limit 8, white balance 32, HDR 4, sharpness 21, wind cut 33,
beep 1, LED 11, auto power off 0 ("never" is ours). The R210's own lists include video at
4096×2048@24, 2880×1440@30, 2560×1280@60/30, 1920×960@30 and 1440×720@120, plus 1920×1080@60/30 and
1280×720@30 with one lens. Every setting was read and written over the API, and a still and a
video were recorded through it.

## Live view, 2026-10-29

The stock remote viewfinder works as on the C200. The plugin starts `CUINETDlnaMan` as
`CUINETFuncDLNA::process_common_activate` does: `StartDlna(man, func + 0x5d4, true, no card)`, with
the manager at `func + 0x608`, without the function's own network bring-up. The camera then listens
on 7676 (UPnP), 7679 (stream) and 9001 (files). ARB2 serves `/livestream_high.avi` only: Samsung's
TTTS stream, 2560×1280, about 19 Mbit/s. `_middle` and `_low` answer 400.

Between clients the stream's camcorder session must be stopped (`CUINETFuncDLNA::dlna_mpeg_stop`),
or the next client gets only the header, or nothing. While the DLNA stack is still sending to a
client that has left ("Cannot send data", until "Streaming Failed"), that stop holds the camera
app's main loop for 10 to 60 s. Stopping the DLNA service first closes those sockets, and then the
session stops at once. So `adapter_r210` opens a live view with stop DLNA, stop session, start
DLNA, and closes it with the first two. Proven in the app: three sessions in a row, the picture on
the phone, the camera app responsive throughout.

## LEDs, 2026-10-29

Mapped on the hardware, one `led.N` at a time: `led.0`–`led.2` are the charge LED red, green and
blue; `led.3` is the lens LED on the display side (green), `led.4` the other lens LED (green);
`led.5`/`led.6` are the same two lens LEDs, red. So 0–4 mean what they mean on the C200, and the
launcher's boot signature (charge blue, one lens, the other, then two flashes) works unchanged.
Seen on the camera. `adapter_r210` offers all seven to the app.

## Reproducing this survey

```sh
docker volume create r210
MSYS_NO_PATHCONV=1 docker run --rm -v "$PWD/firmware/stock:/stock:ro" -v "$PWD/tools:/tools:ro" -v r210:/x g360r-build:1 sh -c '
  cd /x && python3 /tools/slp_unpack.py /stock/R210GLU0ARB2_180201_1739_REV00_user.bin parts &&
  lzop -d -c parts/part06.bin > parts/part06.img && mkdir -p rootfs &&
  debugfs -R "rdump / /x/rootfs" parts/part06.img'
```

Extract on Linux (a Docker volume), not on Windows: a Windows extraction loses the symlinks and
leaves empty files. Decompiling `di-camera-app` and `libdi-network-dlna-api.so` with Ghidra headless
(`blacktop/ghidra`, a DecompileAll post-script) takes about 15 minutes. Function addresses quoted above
are from that ARB2 decompile.
